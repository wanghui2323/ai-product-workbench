## 读者与主问题

读者是产品经理与 AI builder，已经尝试用 Coding Agent 做产品，未必熟悉工程术语。本文独立成立，不属于既有编号系列，不要求读者先理解 RAG 或 Agent 算法。

主问题：怎样让 AI 从一个模糊想法持续推进到可验收的产品，同时保持用户决策、实现范围和完成证据一致？

核心论点：工作台的价值是让同一项用户决策沿稳定关联改变产品方案、实现计划和验收条件，再用对应证据支撑状态；AI 对话、项目记录和网页视图各有明确职责。

读者决策：面对“AI 已经做完”的汇报，能够判断应该继续澄清、开始哪些实现、检查哪种证据，以及哪些工作不应被无关问题拖住。

## 因果主线与知识边界

模糊请求留下隐含选择 → 提关键问题减少方向性歧义 → 比较有实际差异的路线 → 用户明确选择项目内分享 → 同步改变七域方案和任务依赖 → 运行匹配场景的检查 → 用证据声明当前状态 → 安装并复用这一工作方式。

必须解释：来源、用户明确决策与 AI 推荐的区别；范围传播；单一可编辑状态源；受影响工作与独立工作的区分；非 AI 基线；端到端结果与模型输出；实现、本地验证、业务验收、目标交付的证明边界。

工程细节只保留 JSON + 校验生成的运行机制、安装入口和必要状态名。RAG 索引算法、完整权限系统实现、线上实验平台和 Agent 内部规划不展开，以免形成第二主线。全文约 3500–5000 中文字符，以解释完整且无重复为准。

## 示例合同

唯一贯穿示例是明确标注的虚构文档助手：最初提出“团队能问资料，最好答案还能分享给客户”；问谁能看、首个任务与基线、缺证据时如何处理。比较个人使用、项目内分享、外部客户分享。虚构用户明确选择“首版只给项目成员使用，答案项目内分享，并能追到文档原文；客户外链以后再议”。后续所有事实仅作为教学设计，不伪称真实用户访谈、效果、业务运行或实际发布。未决外部渠道仍未选。

七域统一为需求方案、技术方案、技术选型方案、视觉交互 AI 规范、开发计划及模式、测试规范、上线版本管理。图文叫法相同。
