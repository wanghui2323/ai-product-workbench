# 文章内容合同

更新日期：2026-09-12。独立开源实践文章，源稿为 article.md。

## 读者与主问题

读者是尝试用 Coding Agent 开发产品的产品经理与 AI builder，未必熟悉工程术语。文章独立成立，不属于技术基础系列的编号篇，不预设读者理解 RAG 或 Agent 算法。

主问题：怎样把模糊需求推进为有依据的方案、可执行的任务和可验收的版本，让下一轮 AI 协作能继续接手？

核心论点：AI 对话推进理解与决策，项目记录保留事实和关联，网页提供可检查的视图；用户明确决策影响相关需求、方案、计划和检查，证据再约束任务与版本状态。

读者成果：能够打开实际工作台，定位一条未决问题、一项任务依赖和一个版本边界；完成一次需求记录变更，观察关联与页面同步，并确认未实现内容没有被自动标为完成。

## 写作方式与结构

参照 2026-09-12 最新 Agent Memory 技术文章的读者路径，以及其继承的 RAG 终稿：先给可识别的产品问题与完整流程，再讲对象职责、机制、选型代价、分层验证和实际操作。沿用短段落、清晰章节与概念后解释的方式，不复制原文业务例子、技术范围、编号或篇幅。

七节顺序：

1. 对话、记录和网页的分工，以及源文件校验生成的路径。
2. 关键问题为什么影响当前工作，未决事项怎样限定影响范围。
3. 两条可比较方案、各自代价和最小验证，推荐怎样等待明确决策。
4. 需求、技术、选型、视觉交互 AI 规范、开发计划及模式、测试规范、上线版本七域如何承接同一项需求。
5. 任务实现与验收、版本本地验证与目标交付分别需要什么证据。
6. skill 如何把读取与更新协议复用到其他项目，说明现有实现边界。
7. 安装、打开公开示例、在临时目录修改一次需求并校验生成。

以约 4000—5500 中文字符作为篇幅参考，不为凑字数重复概念。正文不写成七域功能清单；技术细节服务于具体行为、依赖和验收。每张图承担一个检查或机制问题，正文解释原因与边界。

正文以公开仓库 examples/document-assistant/docs/workbench/workbench.json 为依据。工作台可运行，文档助手业务完全虚构且未开发验收。截图中的页面能力不能作为文档助手业务运行证据。

- V0.1“可追溯的文档问答”为 planned，范围包括导入、单人资料检索与引用核对；V0.2“团队共享资料”为 candidate；online_version 为 null，evidence 为空。
- Q-SHARE 的选项为“项目内共享”“逐份邀请”，status 为 open，selected_option_id 为空。
- PROP-SHARE“共享资料的最小可用方案”的两项为“按项目统一共享”“按资料单独授权”。前者被有条件推荐，方案 status 为 proposed，selected_option_id 为空。
- “按项目统一共享”以项目作为资料与成员共同访问范围；不混入第二方案的逐资料 ACL。需要讲选择后的联动时，明确使用条件推演，不能伪造用户选择或自动冻结 V0.2。
- 以 REQ-01 的持久处理状态，说明对象合同、前后端任务依赖、界面反馈、测试与版本目标。具体技术栈和状态存储仍为提议，不能写成已选。
- 实操只在临时复制的示例中明确 REQ-01 刷新条件，同步相关任务与页面；已有一致测试保留，所有业务状态与空证据保持。

作者背景可简要说明 LearnBuddy 中的需求、方案与版本整理需要；不编写未核实的详细历史，不引用其他私有业务材料。全文不虚构访谈、用户量、正确率、效益或真实业务结果。
