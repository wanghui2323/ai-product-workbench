# 方案工作台设计合同

在新建、抽取、重构工作台前读。目标不是展示记录齐全，而是让产品判断、技术解释与迭代推进连起来。

## 总览、澄清入口与七个管理域解决不同问题

| 视图 | 用户要判断什么 | 合适的表达 |
|---|---|---|
| 项目总览 | 做什么产品、为谁服务、各模块怎样组成整体 | 定位、角色、模块全景、完整用户旅程、当前/下一版本 |
| 需求澄清与方案决策 | 哪些事实已清楚、什么需要我回答、方案如何选择 | 原始诉求、目标/基线、关键问题、比较选项/推荐理由、自由回答、决策来源；未决事项按关联范围限制后续状态 |
| 需求方案 | 这个模块的用户需要做什么 | 模块选择、价值/JTBD、页面或能力矩阵、交互和状态、优先级、关联需求 |
| 技术方案 | 为什么这么实现、数据怎样流转 | 总体分层、调用关系、端到端数据流、对象生命周期、API、复用策略、难点与对策 |
| 技术选型方案 | 为什么选这个、与替代方案相比代价是什么 | 候选/采用/退役状态，项目约束、备选、理由、风险和决策来源 |
| 视觉交互 AI 规范 | AI 怎样按一致规则实现真实交互 | 原则、Token、组件、状态矩阵、AI执行步骤、浏览器检查 |
| 开发计划及模式 | 为什么改、按什么顺序、如何协作 | 当前迭代 before/after、三件套、过去/当前/下一批次，goal/why/entry/exit、任务依赖与开发模式 |
| 测试规范 | 什么要测、怎样测、凭什么通过 | 分层策略、关键流程/异常、入口、标准、证据合同 |
| 上线版本管理 | 当前交付什么、候选是什么、如何发布与回退 | 版本范围、产物/环境、发布事件、前置门、证据、回滚方案、历史档案 |

小项目可以减少导航层级，但仍应能回答这些问题。CLI 项目把“页面”理解为命令 / 使用入口，不为它发明网页。企业平台的多产品数量、特定技术栈、强制多人评分等不属于通用模板。

## 内容最低质量

一个模块至少说明定位与业务价值、目标用户和用户故事、可执行入口、关键交互、数据对象与状态、技术实现边界。已有架构另有权威文档时保留链接，但工作台不能只剩链接目录。

一个完整用户旅程要从真实触发走到结果，标明角色、动作、输入/输出对象、跨模块交接和关键失败恢复。技术流程应能对照同一旅程，避免“用户流”和“技术图”各讲各的。

架构图需要说明模块责任和关系，数据流需要说明传什么、在哪里存、失败怎么处理。只有技术名词组成的盒子不算解释。可用本地 SVG / HTML；若目标环境支持 Mermaid 也可使用，但图不能依赖一个不可达 CDN 才能读。

版本和开发批次分层：版本是交付边界；批次是工程执行顺序。每批次写为什么此序、依赖、产物和退出条件。不能只给“第一阶段做前端、第二阶段做后端”这种缺乏依赖理由的安排。

## 交互与视觉

如果用户给原作，先打开并阅读实际页面，识别布局层级、内容密度、浏览路径和主要交互，再决定迁移方式。不要先生成通用仪表盘再把字段硬套进去。

默认方案驾驶舱使用顶层 Tab 隔离不同阅读任务。模块全景适合少量导航卡；需求、API 和真实度适合表格；架构适合关系图；批次适合时间线；只读长说明适合有层级的正文。不要所有内容都用相同折叠卡。

桌面支持并列比较；窄屏按阅读顺序重排。宽表可以在受控容器内横向滚动，但关键字段也应能在窄屏读到。状态不只靠颜色。长 ID、长名称、空数据、筛选无结果、复制失败都要有清楚表现。

## 编辑与维护不是同一层

当前随包模板是源文件驱动的本地方案视图。浏览器负责浏览、筛选、下钻、填写回答/选择草稿和复制，AI / 人负责更新源数据并构建。问题是 AI 在会话中主动提出的，静态页不自行调用模型；不要声称网页按钮会保存到仓库。用户明确需要网页直接对话与保存时，按 [实现路线](ai-product-method.md) 补服务层。

若用户明确需要像需求共创工具那样在界面批注或编辑，可追加工作记录层：备注绑定稳定对象 ID，说明本地保存范围，支持校验过的导入与可恢复导出，再与正式源文件合并。不能因有 localStorage 或一个未连接的评论 API 就宣称多人实时同步。
